**The clean-room protocol is the rule that this reference is written entirely from our own work, never copied from the IDML specification, in wording or in structure.**

**In short:** Everything here is our own description of the format. Its rules come from
small files we build ourselves and from what InDesign does when it opens them; what an
open renderer does with the same files comes second. The protocol forbids verbatim or
closely paraphrased wording from the specification and any mirroring of its arrangement,
while treating element and attribute names as the facts they are. Every content change is
confirmed against it, and the specification PDF is never committed to this public
repository.

## Two layers

**Wording.**

- No verbatim text from the specification, its cookbook or any application documentation,
  not even short excerpts.
- No close paraphrase. Rewriting a paragraph by swapping a few words is reproduction, not
  paraphrase. If you are writing with the specification open, close it.
- Element and attribute names are facts, not expression. We use the real XML names because
  they are functional identifiers; naming the thing is not copying the explanation of it.

**Arrangement.**

- No structural mirroring. Copyright protects selection and arrangement, not only
  sentences. A page can be entirely original prose and still be derivative if its
  organisation tracks the specification's table of contents section by section.
- Organise by the reader. Every chapter and page outline is ordered by reader progression
  and reader task. When a reviewer asks "why is this here, in this order?", the answer of
  record is a reader reason, never "because that is the specification's order".
- Describing the format's intrinsic structure (a package genuinely contains these parts; a
  story genuinely nests these ranges) is describing a fact. The line is between describing
  the structure and adopting the specification's presentation of it.

## Sourcing, in order of preference

1. **Files we construct.** Small packages we author, then describe from what we observe.
   They live as unzipped packages in the documentation's
   [`examples/`](https://github.com/paged-media/docs/tree/main/examples) folder.
2. **What InDesign does with them.** InDesign is the authority on how IDML behaves. A file
   is opened in InDesign 20.0.1, and the result is read back through its scripting
   interface and its PDF export. Rules such as "`<Br/>` is the paragraph mark", "the font
   is a typed property", "a missing `ItemTransform` is not identity" or "conditions live in
   the design map" were found only this way: a reader and a writer that share an assumption
   will round-trip a file perfectly and still disagree with InDesign.
3. **What an open renderer does.** The behaviour of the Paged engine and its IDML adapter
   on the same inputs, including edge cases. It shows what a working reader must handle,
   but where it disagrees with InDesign, InDesign wins.
4. **The specification, for orientation only.** To learn which topics exist and what the
   canonical names are; never as a source of explanatory text or organisation. The
   specification PDF is copyrighted vendor material and is **never** committed to this
   repository.

Observing InDesign is itself clean-room work: it records behaviour, not anyone's text.

## How behaviour is measured

The same method runs in three places:

- **The engine.** Paged's engine has a generator that writes IDML fixtures, one feature
  variant per page. InDesign exports each to PDF, and a diff gates the engine's rendering
  against that PDF. A rule measured this way is recorded beside the code that implements
  it ([core ADR 120](https://github.com/paged-media/core/blob/main/docs/adr/120-indesign-is-the-oracle.md)).
- **The IDML adapter.** A spelling rule in Paged's IDML writer counts as correct only
  when InDesign reads the result as intended, not when Paged's own reader reads it back.
  Each rule is recorded as a measurement against a named InDesign version
  ([plugin-publish ADR 653](https://github.com/paged-media/plugin-publish/blob/main/docs/adr/653-indesign-is-the-oracle.md)).
  The rules a writer must follow are collected in
  [what InDesign needs to open a file](/docs/idml/package-anatomy/what-indesign-requires).
- **This reference's examples.** Every example is opened in InDesign, which must open it
  with no missing font or link, save it back as IDML, and export a PDF with the expected
  page count. The PDF pages and the measured difference from Paged's render are stored
  with the example, tied to a hash of its parts, and shown on its InDesign tab. Editing a
  part removes the tab until the example is checked again
  ([docs ADR 806](https://github.com/paged-media/docs/blob/main/docs/adr/806-indesign-verified-examples.md)).
  Separately, every build opens every example in the engine release the site pins and
  checks its page, story, frame, paragraph and run counts.

## Enforcement

Every content change carries a confirmation, *"I have not copied, closely paraphrased, or
structurally mirrored source material in this change"*, which a reviewer checks before
merge. An automated similarity check runs in CI as a backstop where its private baseline
is available: it compares the connective prose of changed pages against a fingerprint of
the specification, with the shared technical vocabulary masked. The fingerprint is not
invertible and is not stored in this repository.

## Frequently asked questions

**What does "clean-room" mean for documentation?**
We write the reference from our own sources, files we construct and what InDesign does
with them, without copying the specification's wording or its arrangement. The result is
an original description of the same format.

**Why is InDesign, not the specification, the source of the rules?**
Because InDesign is what opens the files. Several rules in this reference contradict what a
careful reader of element names would assume, and only opening files in InDesign revealed
them. A specification describes intent; InDesign's behaviour is what a file has to meet.

**Is observing InDesign clean-room?**
Yes. Measuring what an application does with a file records behaviour, not text. Nothing
from InDesign's documentation or the specification is copied.

**Can you use the real element and attribute names from IDML?**
Yes. Names like `Story`, `ParagraphStyleRange` or `ItemTransform` are functional
identifiers, facts rather than protected expression, so we use them freely.

**Is the IDML specification PDF included in this repository?**
No. It is copyrighted vendor material and is never committed. It is consulted only for
orientation: which topics exist and what the canonical names are.

**Why organise the reference differently from the specification?**
Copyright protects selection and arrangement, not just sentences, so mirroring the
specification's structure would make even original prose derivative. Ordering by reader
progression and task also serves readers better.
