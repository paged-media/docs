**The renderer has two rasterizers behind one trait and one rendering model: Vello on
WebGPU is the path you see in the browser, and `vello_cpu`, Vello's CPU renderer, is the
deterministic path of record that keeps it honest.**

**In short:** The final stage of the pipeline turns a [display list](/docs/paged/engine/the-renderer/the-display-list)
into pixels, and it can do so two ways. Both implement the same `PathRasterizer`
trait, so they consume an identical display list. The **WebGPU backend, built on
Vello**, is the forward path — it drives the SDK, the viewer, and this site's live
preview. The **CPU backend, built on `vello_cpu`**, needs no GPU and renders
deterministically, which makes it the path of record: the command line, the fidelity
gates and the editor's CPU snapshots run it. Both lanes draw from one mapping of the
display list into Vello's types, so a difference between them is a difference between
Vello's CPU and GPU renderers, not between two implementations
([ADR 189](https://github.com/paged-media/paged/blob/main/engine/core/docs/adr/189-one-rendering-model.md)).
Releases up to <Fact id="engine.version" />, the one these pages' examples are validated
against, still drew the CPU lane with tiny-skia. This page explains the split and is
honest about where each backend's coverage ends.

## One trait, two implementations

Both backends implement `PathRasterizer`: hand it a `DisplayList` and `RasterOptions`
(page size, DPI, background), get back an RGBA8 buffer. The trait stays deliberately
small so the engine can pick a backend at the edge and the fidelity harness can run
both against the same list.

```rust
pub trait PathRasterizer {
    fn name(&self) -> &'static str;
    fn rasterize(&self, list: &DisplayList, options: &RasterOptions) -> Vec<u8>;
}
```

Notice the contract's honesty clause: a backend that can't render a particular
command should *log and skip it* rather than fail the whole page. That's why a
preview never goes blank because of one unsupported effect — the rest of the page
still draws.

## WebGPU (Vello) — the forward path

The Vello backend drives Vello via `wgpu`, targeting the browser's WebGPU API on the
web and native GPUs elsewhere. This is the path that matters going forward: it's what
the published `@paged-media/sdk` viewer surface uses to load an IDML package and
present it to a canvas, and it's what renders the live preview on this site. Its
output is held to the CPU lane's by a parity gate on every engine change.

The one approximation left is the layer blur, and Vello layers are always isolated, so a
non-isolated group with blending members can differ. Everything else is drawn from the
same geometry and masks as the CPU lane, and the CPU lane stays the reference for
fidelity.

## CPU (vello_cpu) — the path of record

The CPU backend rasterizes the same display list on the CPU with `vello_cpu`, the CPU
renderer of Vello's release train: the same area-coverage antialiasing, gradient ramps,
image sampling and blend formulae as the GPU lane. It earns its place for two reasons
the GPU path can't match:

- **It needs no GPU.** Headless CI runners don't have one. The hard fidelity gate
  runs every fixture through the CPU backend so the check is reproducible anywhere.
- **It is the path of record for fidelity.** What a Vello layer cannot express — a
  non-isolated or knockout group, overprint per ink, a Gaussian-blur layer — the CPU
  rasterizer computes on pixels. When we ask "does our render match InDesign?", the answer
  is measured against the CPU backend's output.

<SupportBadge feature="the-renderer.cpu-backend" note="vello_cpu: the command line, headless CI and the fidelity reference." />

This is why the engine keeps both. The fidelity harness (`paged-fidelity`) diffs the
CPU render against an InDesign-exported reference PDF using ΔE2000 colour difference
and SSIM; that gate is what gives us the confidence to keep evolving the GPU path
without silently regressing. The CPU backend lives behind the default `cpu` feature;
the GPU backend behind `vello-backend`. The published WebGPU viewer build ships no CPU
page rasterizer; it links `vello_cpu` only to draw placed SVGs.

## Which one runs?

It's a build-and-edge decision, not something the display list knows about:

- The **live preview / SDK / viewer** run the **Vello** backend (WebGPU in the
  browser).
- **Headless CI and the fidelity gate** run the **CPU** backend (deterministic, no
  GPU).
- A native tool can pick either; the engine's `render` helpers default to the CPU
  backend when the `cpu` feature is on.

Because both consume the same display list through the same mapping, switching
backends never changes *what* gets drawn; the remaining differences are Vello's own
CPU/GPU differences, a layer blur and isolated groups, and the parity gate bounds them.
The [support badges](/docs/paged/engine/the-renderer/the-display-list) above mark what is
not drawn.

## Frequently asked questions

**If the CPU backend is the fidelity reference, why isn't it the forward path?**
Because faithfulness and interactivity are different jobs. The CPU backend is the
yardstick *because* it's deterministic and needs no GPU, and it computes on pixels what
a GPU layer cannot express — but a live, zoomable, interactive preview wants the GPU. The Vello/WebGPU
backend renders fast enough for the editor and viewer, and the CPU backend keeps it
honest by catching regressions in CI.

**Will the live preview ever look wrong compared to a print render?**
Rarely. Both backends draw from one mapping of the display list, and the soft effects
(shadows, glows, satin, bevel, feathers) come from the same masks on both. What remains
is a Gaussian layer blur, which the GPU replays on a sample grid, and groups that blend
with what is under them, which a GPU layer isolates. Anything not drawn at all carries
a <SupportBadge status="parsed-not-rendered" /> badge.

**Does the live preview need WebGPU support in the browser?**
Yes. The Vello backend targets the browser's WebGPU API. Modern browsers ship it;
where it's unavailable, the preview can't run the GPU path. The CPU backend is not a
browser fallback — it's the headless/CI rasterizer.

**Can I run the renderer without a GPU at all?**
Yes — that's exactly what the CPU (`vello_cpu`) backend is for. Build with the default
`cpu` feature and the engine rasterizes entirely on the CPU, which is how headless CI
and the fidelity harness operate.
