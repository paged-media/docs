**In short:** `paged.data` turns data into pages — a binding-expression DSL, a
resolution/sync engine, record-flow lowering with grouping and per-group footers,
and end-to-end print automation, over a SQL store inside its own engine (Turso, an
in-memory Rust implementation of SQLite). It also publishes governed datasets that
other plugins (e.g. [paged.sheet](/docs/paged/plugins/sheets)) consume.

## What it does

- A publishing-grammar binding DSL (<Fact id="data.functions" /> registry-driven
  functions) and a binding/sync engine (Linked / Pinned / Overridden / Stale states).
- Record flow / pagination: nested grouping, multi-level per-group footers,
  parent-path on spill.
- Print automation: per-record / per-group / one-catalog batch plans, plus a CLI
  and a sandboxed Boa scripting path.
- A data-provider contract: register as a provider and publish a record set
  without knowing its consumers; governed extracts with column metadata.
- InDesign Data Merge: `<<field>>` templates are planned (shipped) and merged into
  one document or one per record by `paged merge` in the Node command line with
  this module installed
  (experimental); see [Coming from Adobe InDesign Server](/docs/paged/use-cases/indesign-server).
- Typed commands for everything the command line's data verbs do — importing a
  source, previewing a query, defining bindings (expression property bindings
  included), applying, merging and planning a batch — plus read-only checks of
  an expression, a refresh's changes and a record flow; `paged generate` writes
  one document per record or per group from them
  ([paged.data commands](/docs/paged/commands/data)).
- Sources read in Rust into the store: CSV and TSV (the delimiter sniffed, each
  column typed — integer, decimal, real, boolean, date, timestamp, else text — and
  the file also kept as written for Data Merge), JSON, Parquet and XLSX. A query is
  SQLite's dialect: one guarded, read-only statement over the document's tables.
- New on `main`, experimental:
  - **Transforms** — JavaScript functions over tables, saved with the document and
    run in a sandboxed interpreter after the sources and before the queries; their
    rows are a derived, read-only table that queries and bindings read.
  - **Picture columns** — a field of image URLs or paths placed as pictures:
    fetched only from origins the user consented to, kept by content hash, run
    through a chain of image actions (resize, fit, crop and others from
    [paged.image](/docs/paged/plugins/image)), and saved inside the `.paged`.
  - **Record status** — which records are new, changed or gone since the
    document was made from the data, and where each record is placed.
  - **Data issues** — text that does not fit its frame (a table cell by row and
    column), a missing picture or one under 150 ppi in its frame, an empty value,
    a failed binding, records a flow left out: listed in the Problems panel and
    marked on the canvas, before print.
  - **The data door** (`data@1` in the plugin SDK) — other modules and extensions
    read the document's tables and records through it, and write rows of an
    imported table; [paged.sheet](/docs/paged/plugins/sheets) edits a table this
    way.
- In development: export as a Data Merge template, the SQL query panel, row diffs
  and sync review, and binding any object property to data (the universal binding
  round).

## How it's built

Rust crates in the engine's Cargo workspace (`paged-data-core`, `-expr`,
`-sources`, `-query`, `-store`, `-xlsx`, `-bind`, `-lower`, `-dataset`,
`-barcode`, `-automation`, `-session`) compiled into one wasm by `data-js`, plus
a TS bundle (`@paged-media/data`). The SQL store is Turso inside that wasm;
transforms run on the engine's action interpreter, with no host functions and a
step budget.
