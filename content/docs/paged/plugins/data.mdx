**In short:** `paged.data` turns data into pages — a binding-expression DSL, a
resolution/sync engine, record-flow lowering with grouping and per-group footers,
and end-to-end print automation, all over a vendored DuckDB-WASM. It also
publishes governed datasets that other plugins (e.g.
[paged.sheet](/docs/paged/plugins/sheets)) consume.

## What it does

- A publishing-grammar binding DSL (<Fact id="data.functions" /> registry-driven
  functions) and a binding/sync engine (Linked / Pinned / Overridden / Stale states).
- Record flow / pagination: nested grouping, multi-level per-group footers,
  parent-path on spill.
- Print automation: per-record / per-group / one-catalog batch plans, plus a CLI
  and a sandboxed Boa scripting path.
- A data-provider contract: register as a provider and publish a record set
  without knowing its consumers; governed extracts with column metadata.
- InDesign Data Merge: `<<field>>` templates are planned (shipped) and merged into
  one document or one per record by `paged merge` in the Node command line with
  this module installed
  (experimental); see [Coming from Adobe InDesign Server](/docs/paged/use-cases/indesign-server).
- Typed commands for everything the command line's data verbs do — importing a
  source, previewing a query, defining bindings (expression property bindings
  included), applying, merging and planning a batch — plus read-only checks of
  an expression, a refresh's changes and a record flow; `paged generate` writes
  one document per record or per group from them
  ([paged.data commands](/docs/paged/commands/data)).
- In development: export as a Data Merge template, a SQL query panel over DuckDB,
  local JSON, Parquet and XLSX sources, row diffs and sync review, and binding any
  object property to data (the universal binding round).

## How it's built

A Cargo workspace (`data-core`, `data-expr`, `data-sources`, `data-query`,
`data-bind`, `data-lower`, automation crates, `data-js`) plus a TS bundle, with
DuckDB-WASM vendored behind an Arrow seam.
